# 1. Doze Mode란?

퇴근하고 집에 와서 폰을 책상 위에 딱 올려두고 잠들었다고 생각해보자. 화면은 꺼져 있고, 아무도 폰을 건드리지 않고, 충전도 안 하고 있다. 이 상태로 6시간이 지났다.

이때 폰 안에서는 무슨 일이 벌어질까? 만약 아무 제약이 없다면, 카톡은 30초마다 서버에 "새 메시지 있어?" 물어보고, 날씨 앱은 1분마다 위치를 갱신하고, 이런저런 앱들이 각자 타이머를 돌리면서 CPU와 네트워크를 계속 깨운다. 사용자는 자고 있는데 폰 혼자 밤새 파티를 하는 셈이다. 아침에 일어나면 배터리는 반토막.

Doze Mode는 이런 상황을 막기 위해 Android 6.0(마시멜로, API 23)부터 들어간 시스템 절전 기능이다. 한마디로 정의하면:

> "기기가 아무도 안 건드리고 가만히 있는 상태가 일정 시간 지속되면, 시스템이 나서서 모든 앱의 백그라운드 활동을 강제로 멈추거나 미뤄버리는 모드"

여기서 핵심 단어는 "강제로"다. 개발자가 "우리 앱은 백그라운드에서 계속 돌아야 해요"라고 아무리 우겨도, 기기가 Doze Mode에 들어가면 시스템이 이를 무시하고 억누른다. 앱 개발자 입장에서는 살짝 억울할 수도 있지만, 사용자 배터리를 지키기 위한 최소한의 장치라고 보면 된다.

<br>

# 2. 왜 Doze Mode가 필요한가?

Doze Mode가 없던 시절(Android 5.x 이전)을 떠올려보자. 그때는 이런 문제들이 흔했다.

**문제 1. 다들 각자 알아서 깨어난다**

앱 A는 5분마다, 앱 B는 3분마다, 앱 C는 정확히 밤 12시에 깨어나서 뭔가를 한다. 사용자 입장에서는 폰이 쉴 새 없이 CPU를 켰다 껐다 반복하는 셈이다. 마치 기숙사에서 룸메이트들이 각자 다른 시간에 알람을 맞춰놓고 매번 방 불을 켰다 껐다 하는 것과 비슷하다. 한 명 한 명은 잠깐이지만, 합쳐지면 밤새 아무도 못 잔다.

**문제 2. WakeLock을 놓고 안 놓는 앱**

어떤 앱이 "나 지금 중요한 작업 중이니까 CPU 재우지 마"라고 WakeLock을 걸어놓고, 작업이 끝났는데도 깜빡하고 해제를 안 하면? 폰은 화면이 꺼져 있어도 속으로는 계속 깨어있는 상태가 되어 배터리가 줄줄 샌다. 실제로 이런 버그를 가진 앱들이 배터리 소모 순위 1위를 다투곤 했다.

**문제 3. 네트워크 라디오가 계속 켜진다**

네트워크 요청 한 번 하려면 셀룰러/Wi-Fi 라디오를 깨워야 하는데, 이게 꽤 전력을 먹는다. 여러 앱이 제각각 다른 타이밍에 네트워크를 쓰면 라디오가 잠들 틈이 없다.

Doze Mode는 이 모든 "제각각 깨어나는" 상황을 시스템이 교통정리해서, "자, 다들 조용히 있다가 내가 문 열어줄 때만 한꺼번에 처리해"라는 식으로 바꿔버린 것이다. 뒤에 나올 Maintenance Window가 바로 그 "문 열어주는 시간"이다.

<br>

# 3. Doze Mode 진입 조건

Doze Mode는 아무 때나 훅 들어오는 게 아니라, 다음 조건이 전부 충족되어야 진입한다.

- 화면이 꺼져 있음
- 충전 중이 아님
- 일정 시간(대략 30분 안팎) 동안 기기의 움직임이 감지되지 않음 (가속도계 기준)

이 세 가지가 동시에 만족되면 시스템은 "아, 이 사용자는 지금 폰을 안 쓰고 있구나"라고 판단하고 Doze Mode로 서서히 들어간다.

재밌는 점은, 이 진입이 한 번에 딱 켜지는 스위치가 아니라 **단계적으로 깊어진다**는 것이다. 처음엔 살짝만 제약을 걸다가, 시간이 더 지나면 점점 더 강하게 조인다. 마치 사람이 잠들 때 얕은 잠에서 시작해서 점점 깊은 잠으로 빠지는 것과 비슷한 그림이다.

그리고 Doze Mode는 다음 중 하나만 일어나도 즉시 풀린다.

- 사용자가 화면을 켠다
- 충전기를 꽂는다
- 기기를 집어 들어 움직인다

즉, Doze Mode는 "완전히 방치된 상태"에서만 유지되는 매우 조심스러운 모드다.

**참고로**, Android 7.0(누가, API 24)부터는 조건이 하나 더 생겼다. 화면이 꺼진 채로 가방이나 주머니에 넣고 이동 중이어도(즉 완전히 정지 상태가 아니어도), 일정 시간이 지나면 진입하는 "Doze on the go(라이트 Doze)"가 추가됐다. 예전에는 "책상 위에 가만히 두고 자야만" 절전이 됐다면, 이제는 "주머니에 넣고 돌아다녀도" 어느 정도 절전이 적용되는 것이다.

<br>

# 4. Doze Mode에서 제한되는 작업

Doze Mode에 깊이 들어가면 다음과 같은 것들이 줄줄이 묶인다.

- **네트워크 접근 차단**: 앱이 인터넷에 접근하려 해도 요청이 나가지 않는다
- **WakeLock 무시**: 앱이 WakeLock을 잡고 있어도 시스템이 그냥 CPU를 재워버린다
- **알람 지연**: `AlarmManager`의 일반 알람(`setExact`, `setWindow` 등)이 예정된 시각에 안 울리고 미뤄진다
- **JobScheduler 작업 보류**: 예약된 백그라운드 작업이 실행되지 않고 대기 상태로 쌓인다
- **동기화 중지**: `SyncAdapter` 기반 자동 동기화가 멈춘다
- **Wi-Fi 스캔 중지**: 주변 Wi-Fi를 찾는 스캔 작업도 멈춘다

비유하자면, Doze Mode는 아파트 관리사무소가 "밤 12시부터 아침 6시까지는 택배도 안 받고, 세탁기도 못 돌리고, 공사 소음도 금지입니다"라고 못박아버리는 것과 비슷하다. 입주민(앱)이 아무리 "저 지금 급한데요"라고 해도 예외는 거의 없다.

**예외는 있다.** 다음 두 가지처럼 "이건 정말 중요하다"고 시스템이 인정하는 API는 Doze 중에도 동작한다.

- `setAlarmClock()`: 사용자가 설정한 알람시계는 Doze 중에도 정확히 울려야 한다. 자명종이 안 울리면 큰일 나니까.
- `setExactAndAllowWhileIdle()`: "정말 예외적으로 유휴 상태에서도 꼭 실행되어야 하는" 알람을 등록할 때 쓴다. 다만 이것도 남발하면 시스템이 실행 빈도를 제한한다.

<br>

# 5. Maintenance Window란?

그럼 Doze Mode 동안 밀린 작업들은 영영 실행 안 되는 걸까? 그건 아니다. 시스템은 주기적으로 아주 짧은 "숨 쉴 틈"을 열어주는데, 이걸 **Maintenance Window(유지보수 구간)**라고 부른다.

비유하면, 앞서 말한 아파트 관리사무소가 "그래도 하루에 몇 번은 잠깐씩 택배 받는 시간을 열어드릴게요"라고 배려해주는 것과 같다. 이 짧은 구간 동안은:

- 네트워크 접근이 다시 허용된다
- 밀려있던 알람, 동기화, JobScheduler 작업이 한꺼번에 처리된다
- WakeLock도 정상적으로 동작한다

그리고 이 창문이 열리는 패턴이 재미있다. Doze Mode가 막 시작됐을 때는 비교적 자주(예: 몇 분 간격으로) 창문이 열리다가, 유휴 상태가 길어질수록 창문 간격은 점점 길어지고(몇 시간 단위로), 대신 한 번 열릴 때 짧게 열린다. 즉 "오래 방치될수록 문 여는 횟수도 줄고 여는 시간도 짧아진다"는 뜻이다. 하룻밤 내내 방치된 폰이라면, 마지막 즈음엔 창문이 몇 시간에 한 번, 그것도 아주 잠깐만 열릴 수 있다.

그래서 "Doze 중에도 언젠가는 실행되긴 하는데, 정확히 언제 실행될지는 시스템 맘"이라는 게 핵심 포인트다. 이걸 이해하고 있어야 "왜 내 알람이 정시에 안 울리지?" 같은 버그 리포트에 당황하지 않는다.

<br>

# 6. Doze Mode와 WakeLock의 관계

WakeLock은 원래 "이 작업 끝날 때까지 CPU 재우지 마세요"라고 시스템에 부탁하는 장치다. 평소에는 이 부탁이 잘 지켜진다.

그런데 Doze Mode에 들어가면 이야기가 달라진다. **이미 잡아놓은 WakeLock이 있어도 시스템은 그냥 CPU를 재워버린다.** 즉:

- Doze 진입 **전**: WakeLock이 정상적으로 CPU를 깨운 채로 유지시켜줌
- Doze 진입 **후**: WakeLock은 사실상 무시되고, Maintenance Window가 열릴 때만 잠깐 유효해짐

이건 마치 "나 지금 회의 중이니까 방해하지 마세요" 팻말을 문에 걸어놨는데, 건물 전체 소등 시간이 되니까 관리인이 "죄송한데 규정이라 어쩔 수 없어요" 하면서 불을 꺼버리는 것과 비슷하다. 개별 부탁(WakeLock)보다 전체 규칙(Doze Mode)이 우선한다.

그래서 다운로드, 동기화, 위치 추적처럼 "오래 걸리는 백그라운드 작업"을 WakeLock 하나만 믿고 짜면, Doze Mode에 걸리는 순간 작업이 뚝 끊기거나 예상치 못하게 지연된다. 이런 이유로 요즘은 WakeLock을 직접 다루기보다, 뒤에서 설명할 **WorkManager**처럼 Doze Mode를 이미 고려해서 설계된 라이브러리를 쓰는 게 정석으로 자리 잡았다.

<br>

# 7. App Standby란?

Doze Mode가 "기기 전체가 방치됐을 때"의 이야기라면, App Standby는 "이 앱 하나가 방치됐을 때"의 이야기다. 역시 Android 6.0에서 Doze Mode와 함께 태어난 형제 기능이다.

정의하면:

> "사용자가 특정 앱을 최근에 실행하지 않았다고 판단되면, 그 앱만 콕 집어서 '미사용(idle)' 상태로 분류하고 백그라운드 네트워크 접근 등을 제한하는 기능"

예를 들어 폰에 앱이 100개 깔려있는데, 그중 카톡이나 유튜브처럼 매일 쓰는 앱은 시스템이 "얘는 활발하게 쓰는구나" 하고 봐주지만, 3개월 전에 딱 한 번 써보고 방치한 어떤 앱은 "얘는 이제 안 쓰는구나" 판단해서 백그라운드 활동을 강하게 억제한다.

App Standby로 분류되는 대표적인 기준:

- 사용자가 앱을 일정 시간 이상 직접 실행하지 않음
- 포그라운드 알림이나 화면에 보이는 활동이 없음

여기서 중요한 차이가 하나 있다. Doze Mode는 "기기 전체"에 걸리는 셔터라서, 자주 쓰는 앱이든 안 쓰는 앱이든 다 같이 멈춘다. 반면 App Standby는 "앱 개개인의 평판"을 보고 차등 대우를 한다. 마치 학교 도서관이 시험 기간엔 다 같이 문을 닫는 것(Doze)과, 평소에 자주 오는 단골 학생에게만 열람실 우선 좌석을 주는 것(App Standby)의 차이라고 보면 된다.

<br>

# 8. App Standby Bucket이란?

처음엔 App Standby가 "쓰는 앱 vs 안 쓰는 앱" 이렇게 단순한 on/off였는데, Android 9(파이, API 28)부터 훨씬 정교해졌다. 앱을 사용 패턴에 따라 5개의 등급(Bucket)으로 나눈 것이다.

| 버킷 | 의미 | 비유 |
|---|---|---|
| Active | 지금 사용 중이거나 포그라운드에 있음 | 지금 대화 중인 친구 |
| Working set | 자주 사용하는 앱 | 매일 연락하는 친구 |
| Frequent | 어느 정도 자주 쓰는 앱 | 가끔 연락하는 친구 |
| Rare | 거의 안 쓰는 앱 | 1년에 한두 번 연락하는 지인 |
| Restricted | 오랫동안 방치되어 강하게 제한되는 앱 | 번호는 있는데 누군지 기억 안 나는 사람 |

버킷이 아래로 갈수록(Rare, Restricted) JobScheduler 실행 빈도, 네트워크 접근 허용량, FCM 메시지 처리 우선순위 등이 점점 더 짜게 제한된다. Restricted 버킷에 들어간 앱은 백그라운드에서 사실상 거의 아무것도 못 한다고 봐도 된다.

이 분류는 사람이 수동으로 정하는 게 아니라, 시스템이 사용자의 실제 사용 패턴을 계속 관찰하고(심지어 머신러닝 기반 예측까지 곁들여서) 앱을 버킷 사이로 자동으로 승격/강등시킨다. 오랜만에 앱을 다시 켜면 버킷이 다시 올라가고, 또 방치하면 다시 내려가는 식으로 계속 움직인다.

<br>

# 9. Doze Mode와 App Standby의 차이

지금까지 내용을 표로 정리하면 훨씬 머리에 잘 들어온다.

| 구분 | Doze Mode | App Standby |
|---|---|---|
| 기준 단위 | 기기 전체 | 개별 앱 |
| 트리거 조건 | 화면 꺼짐 + 정지 + 미충전 | 앱을 오래 안 씀 |
| 적용 범위 | 모든 앱이 동시에 제한됨 | 앱마다 버킷에 따라 다르게 제한됨 |
| 해제 조건 | 화면 켜짐, 충전, 움직임 | 앱을 다시 실행하거나 포그라운드로 전환 |
| 비유 | 아파트 전체 소등 시간 | 개인별 출입 등급 |

가장 헷갈리기 쉬운 부분은 "이 둘이 서로 배타적이지 않다"는 점이다. 즉:

- Doze Mode가 **아닐 때**도, 특정 앱은 App Standby 때문에 개별적으로 제한받을 수 있다 (예: 화면은 켜져 있고 폰도 쓰고 있지만, 한 달 동안 안 켠 어떤 앱은 그동안 여전히 억제된다)
- Doze Mode에 **들어가면**, 모든 앱이 추가로 더 강하게 제한받는다 (기존에 Active 버킷이던 앱조차도)

정리하면 두 시스템은 독립적으로 동시에 작동하는 이중 안전장치라고 보면 된다.

<br>

# 10. 백그라운드 작업에 미치는 영향

이 두 기능이 실제 앱 동작에 어떤 영향을 주는지 구체적으로 짚어보자.

- 실시간성이 필요한 백그라운드 네트워크 요청이 예상보다 늦게 나갈 수 있다
- 채팅 앱의 폴링처럼 "주기적으로 서버 확인하기" 로직이 예정된 시각보다 한참 늦게 실행될 수 있다
- `AlarmManager`로 "정확히 이 시각에 실행"이라고 예약한 작업이 밀릴 수 있다
- FCM(푸시 알림)도 일반 우선순위 메시지는 Maintenance Window까지 지연될 수 있다 (고우선순위 메시지만 예외적으로 즉시 전달됨)

여기서 개발자가 얻어야 할 태도 전환이 하나 있다. 예전에는 "내가 원하는 시각에 정확히 실행되겠지"라는 전제로 설계했다면, Doze Mode 이후로는 **"언젠가는 실행되지만, 정확한 타이밍은 시스템이 결정한다"**는 전제로 바꿔야 한다. 사용자에게 실시간성을 보장해야 하는 기능(예: 긴급 알림, 통화)이 아니라면, "지연 허용형" 설계가 기본값이 되어야 한다.

<br>

# 11. WorkManager와의 관계

여기서 등장하는 게 바로 **WorkManager**다. Jetpack 라이브러리 중 하나로, 애초부터 "Doze Mode와 App Standby가 존재하는 세상"을 전제로 설계됐다.

WorkManager가 하는 일을 요약하면:

- API 레벨에 따라 내부적으로 JobScheduler, AlarmManager, BroadcastReceiver 중 가장 적절한 방식을 알아서 골라 사용한다 (개발자가 직접 분기 처리할 필요 없음)
- Doze Mode 중이라면, 시스템의 Maintenance Window에 맞춰서 작업이 실행되도록 시스템과 협력한다 (즉 시스템 규칙을 어기지 않으면서 최대한 빨리 실행되도록 스케줄링)
- `setExpedited()`를 쓰면 "이 작업은 좀 급해요"라고 우선순위를 높여서 거의 즉시 실행에 가깝게 처리할 수 있다. 다만 이것조차 시스템의 절전 제약을 완전히 무시하지는 못한다

즉, 예전처럼 개발자가 직접 WakeLock 잡고, AlarmManager 등록하고, Doze Mode 예외 처리까지 손수 하던 시절과 비교하면, WorkManager는 "그런 복잡한 걸 내가 대신 챙겨줄게, 너는 그냥 무슨 일을 할지만 알려줘"라고 해주는 든든한 매니저 같은 존재다.

그래서 오늘날 Android 개발 기준으로는, 즉시 실행이 반드시 필요한 아주 짧은 작업이 아니라면 **AlarmManager나 WakeLock을 직접 만지기보다 WorkManager를 쓰는 것이 사실상 표준**이다.

<br>

# 12. 배터리 최적화 예외

그렇다면 정말로 백그라운드에서 실시간으로 계속 동작해야 하는 앱(예: 카톡 같은 메신저, 인터넷 전화 앱)은 어떻게 할까?

사용자가 직접 특정 앱에 대해 "배터리 최적화 무시" 권한을 부여하면, 그 앱은 Doze Mode의 제약을 상당 부분 우회할 수 있다.

- 설정 > 배터리 > 배터리 최적화 메뉴에서 앱별로 예외 설정 가능
- 앱이 `ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` 인텐트를 띄워서 사용자에게 직접 예외 요청을 할 수도 있음
- 주로 VoIP(인터넷 전화), 알람, 메시징 앱처럼 "즉시성이 생명"인 앱들이 이 예외를 필요로 함

다만 여기엔 함정이 있다. Google Play 정책상 이 예외 요청은 "앱의 핵심 기능이 실시간 백그라운드 동작을 필수로 요구하는 경우"에만 정당화된다. 아무 앱이나 "우리도 배터리 최적화 빼주세요" 하고 팝업을 띄우면, 스토어 심사에서 반려당할 수 있다. 사용자 배터리를 보호하려고 만든 기능인 만큼, 예외를 남발하는 걸 구글도 곱게 보지 않는다.

# 13. 실전에서 주의해야 할 점

이론은 여기까지고, 실제로 개발하고 테스트할 때 알아두면 좋은 것들을 모아봤다.

**Doze Mode를 강제로 재현해보기**

실기기에서 30분씩 기다릴 수 없으니, adb 명령으로 강제 진입시켜서 테스트할 수 있다.

```bash
adb shell dumpsys deviceidle force-idle
```

테스트가 끝나면 강제 상태를 풀어준다.

```bash
adb shell dumpsys deviceidle unforce
```

**에뮬레이터만 믿지 말기**

에뮬레이터나 평소 개발 환경에서는 Doze Mode나 App Standby가 실제 기기만큼 엄격하게 재현되지 않는 경우가 많다. "내 컴퓨터에선 잘 되는데요" 함정과 비슷하게, "에뮬레이터에선 잘 되는데요" 함정에 빠지지 않으려면 실기기 테스트가 꼭 필요하다.

**FCM 메시지 우선순위 설정하기**

즉시 전달이 꼭 필요한 푸시라면, 일반 메시지가 아니라 고우선순위(high priority) 메시지로 보내야 Doze 중에도 지연 없이 전달될 가능성이 높아진다.

**지연을 감안한 UX 설계하기**

백그라운드 위치 추적, 실시간 동기화 같은 기능을 만들 때는 "지연될 수 있다"는 걸 사용자에게도 자연스럽게 알려주는 UX가 필요하다. 예를 들어 화면에 "마지막 동기화: 3분 전"처럼 표시해주면, 사용자가 "왜 안 되지?"라고 당황하지 않고 상황을 이해할 수 있다.

<br>

# 14. 정리

- Doze Mode는 "기기 전체"가 방치됐을 때, App Standby는 "개별 앱"이 방치됐을 때 각각 백그라운드 작업을 제한하는 Android의 이중 배터리 절전 장치다.
- 두 기능은 서로 독립적으로 작동하지만, 같이 맞물려서 불필요한 백그라운드 활동을 대폭 줄여준다. 개발자 입장에서 가장 중요한 태도 변화는 "내가 원하는 시각에 정확히 실행되겠지"가 아니라 "언젠가는 실행되지만, 정확한 타이밍은 시스템이 결정한다"는 전제로 설계를 바꾸는 것이다.
- 그리고 실무에서는 WakeLock이나 AlarmManager를 직접 다루기보다, 이미 이 모든 걸 고려해서 만들어진 **WorkManager**를 활용하는 게 훨씬 안전하고 편하다. 정말로 실시간성이 생명인 기능에 한해서만 배터리 최적화 예외 같은 특수 처리를 신중하게 고려하면 된다.
